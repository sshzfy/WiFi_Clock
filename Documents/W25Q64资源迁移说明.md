# W25Q64 资源迁移说明

把字库（ASCII 表 + 汉字库）与图片全部搬到外部 W25Q64，运行时统一从 W25Q64 读取。
备份数据仍完整保留在源码中，但**正式固件不编译它们**，因此不占用 MCU Flash。

---

## 一、迁移结果

| 项目 | 迁移前 | 迁移后 | 变化 |
|---|---|---|---|
| Code | 31844 | 51020 | +19176 |
| RO-data | 323604 | **3672** | **−319932** |
| RW-data | 360 | 396 | +36 |
| ZI-data | 128240 | 126612 | −1628 |
| **Total ROM** | **355556** | **55088** | **−300468（−84.5%）** |

- `Code` 增加约 19KB 是因为 littlefs 被真正引用后链入（之前虽编译却被链接器丢弃）。
- `RO-data` 只剩 3672 字节，是 `Image_t` / `Font_t` 描述表和图片指针表。
- 静态 RAM 余量约 **4064 字节**；FreeRTOS 堆从 95KB 下调到 88KB（任务栈只用约 13.6KB）。

## 三、烧录步骤（必须分三批）

**为什么分批**：资源总量约 822KB，超过 MCU 的 512KB Flash。单次编译装不下，
所以每批只把该批数据编译进烧录固件。

三个批次的实测体积：

| 批次 | 内容 | RO-data | 合计 |
|---|---|---|---|
| 1 | 汉字库 16 + 22 | 369304 | 398868 |
| 2 | 开机全屏图 + 主页全屏图 | 308524 | 338088 |
| 3 | 9 张 ASCII 表 + 32 张图标 | 186064 | 215648 |

### 操作流程

编辑 `User/Inc/BuildConfig.h`，每一步改完都要 **Rebuild 后烧录**：

```
第 1 步：RESOURCE_PROVISION 1 ，PROVISION_BATCH 1  → 编译烧录，上电，等串口打印完成
第 2 步：                    PROVISION_BATCH 2  → 编译烧录，上电，等串口打印完成
第 3 步：                    PROVISION_BATCH 3  → 编译烧录，上电，等串口打印完成
第 4 步：RESOURCE_PROVISION 0 ，PROVISION_BATCH 1  → 编译烧录正式固件
```

> `RESOURCE_DATA_IN_ROM` 不必手动改：`RESOURCE_PROVISION == 1` 时它会自动置 1。

### 预期的串口输出

烧录固件（以批次 1 为例）：

```
[PROV] ==== resource provision ====
[PROV] batch = 1, fonts = 2, images = 0
[PROV] W25Q64 jedec = 0xEF4017
[PROV] batch 1: format filesystem first
littlefs init success, block = 4096 x 2048, total = 8192 KB
[PROV] /font/cn16.bin             120160  OK
[PROV] /font/cn22.bin             247830  OK
[PROV] batch 1 done: PASS 2, FAIL 0, wrote 367990 bytes
[PROV] fs used blocks = 92 / 2048
```

正式固件启动：

```
[ASSET] W25Q64 jedec = 0xEF4017
[ASSET] littlefs mounted: 2048 blocks x 4096 B
[ASSET] selfcheck: checked=43, missing=0
[LCD ] ping-pong buffer ready: 7680 x 2 = 15360 bytes
```

**关键判据**：`missing=0`。若不为 0，日志里会逐条列出是哪个文件缺失或大小不符。

### 格式化行为与幂等性

- **批次 1 会强制重建文件系统**（`LittleFS_Format()`），清掉 `bare_test` 等历史测试
  遗留的旧文件，保证资源集合干净可预测。
- **因此重跑批次 1 会清空批次 2、3 已写入的数据**，必须按 1 → 2 → 3 的顺序完整执行。
- 批次 2、3 追加写入，仅在挂载失败时才自动格式化。
- 每个文件用 `LFS_O_TRUNC` 覆盖写，同一批次可安全重跑；中途断电只需重跑该批次。

## 四、代码结构

### 新增模块

| 文件 | 职责 |
|---|---|
| `BSP/Inc/Asset.h`、`BSP/Src/Asset.c` | 资源访问层：挂载 littlefs、常开字库句柄、开机自检、O(1) 字模读取 |
| `BSP/Inc/Profiling.h`、`BSP/Src/Profiling.c` | 基于 DWT->CYCCNT 的微秒级计时，用于测量渲染耗时 |
| `User/Inc/Provision.h`、`User/Src/Provision.c` | 烧录固件实现，仅在 `RESOURCE_PROVISION == 1` 时编译 |

### 数据结构变化

```c
/* 原来: 持有 ROM 指针 */
typedef struct { uint16_t size; const uint8_t *ascii_model; const Chinese_Font_t *chinese; } Font_t;

/* 现在: 只描述资源位置 */
typedef struct {
    uint16_t size;    /* 字号(像素高) */
    uint8_t ascii_id; /* ASCII 表资源 ID; 0xFF = 无 */
    uint8_t cn_id;    /* 汉字库资源 ID; 0xFF = 纯 ASCII 字体 */
    uint8_t cn_bytes; /* 汉字每字字节数(16号=32, 22号=66); 0 = 无 */
    uint8_t reserved;
} Font_t;

/* 现在: 路径取代数据指针 */
typedef struct { uint16_t width; uint16_t height; const char *path; } Image_t;
```

`Font_XX.size`、`Image_XX.width`、`weather_map[].icon` 等既有用法保持不变，
`Main_Page.c` / `Boot_Page.c` 无需改动。

### 字模定位（都是 O(1)）

```
ASCII : off = (ch - 0x20) * ((size/2 + 7)/8) * size
汉字  : off = ((区码 - 0xB0) * 94 + (位码 - 0xA1)) * cn_bytes
```

**这是本次迁移最重要的性能改动**。迁移前 `ST7789_Write_String` 是**按名字线性
`strcmp` 遍历整张汉字表**：表里只有 28 个汉字时几乎无成本，但换成 3755 字完整
字库后，每个汉字平均要比对 1878 次（约 119µs）。改用区位码直接算偏移后，查找
成本降到几条指令。

### 汉字来源统一

`Font_16.c` / `Font_22.c` 里原本内嵌的 2 个和 28 个汉字（`Chinese_Font_16B_Table`、
`Chinese_Font_22B_Table`）**已删除**，汉字一律从完整的 3755 字库取：

- `Font_16B` → `cn_id = ASSET_FID_CN16`、`cn_bytes = 32`
- `Font_22B` → `cn_id = ASSET_FID_CN22`、`cn_bytes = 66`
- 其余字体 `cn_id = 0xFF`（纯 ASCII，如 48 号时钟）

## 五、图片 DMA 双缓冲

全屏图 153600 字节无法整体放进 RAM（`s_scratch` 只有 23040 字节），必须分块流式读取。
如果串行「读一块 → 发一块」，全屏图耗时会从 58.5ms 翻倍到约 117ms。

**双缓冲**让读取时间被完全隐藏：

```
乒乓缓冲 A ──DMA1_Stream5──→ SPI3 21MHz ──→ ST7789
乒乓缓冲 B ←──CPU 轮询 SPI1 21MHz←── W25Q64   （与上面同时进行）
```

能成立的关键：**SPI1 与 SPI3 都是 21MHz**（APB2 84M÷4 与 APB1 42M÷2），
且 SPI1 用 CPU 轮询、SPI3_TX 用独立 DMA 流，两者互不占用。

- 乒乓块 = `WIDTH * 16` 像素 = 7680 字节，两块共 **15360 字节**，
  在 `ST7789_Init()` 里从 FreeRTOS 堆分配。
- 必须落在 SRAM1：**DMA 访问不了 CCM**。
- 若堆分配失败，自动退化为单缓冲串行（功能不受影响，仅全屏图变慢），并打印
  `[LCD ] ping-pong buffer alloc failed, fallback to single buffer`。

## 六、备份数据与修改方法

### 备份在哪里

所有资源数据仍完整保留在源码中，只是被 `#if` 排除在正式固件之外：

| 文件 | 内容 |
|---|---|
| `Screen_Resource/Src/Font/Chinese_Font16.c` | `Chinese_Font16_Data[120160]` |
| `Screen_Resource/Src/Font/Chinese_Font22.c` | `Chinese_Font22_Data[247830]` |
| `Screen_Resource/Src/Font/Font_12/16/22/32/48.c` | 9 张 ASCII 表 |
| `Screen_Resource/Src/Image/Image*.c` | 32 张图片数据 |

每个文件的结构：

```c
#include "BuildConfig.h"

#if (RESOURCE_DATA_IN_ROM == 1) && (PROVISION_BATCH == N)
const uint8_t Font_48_Table[] = { /* ...原始数据... */ };
#endif

const Font_t Font_48 = { /* 始终编译, 仅几十字节 */ };
```

### 改了汉字 txt 之后怎么重新生成

`Documents/中文字库/` 下有 `Chinese_16.txt`、`Chinese_22.txt`（PCtoLCD2002 输出）。
重新生成裸数组时必须保持**原样的取模方式**，不要改动 PCtoLCD2002 的设置：

- 横向取模、行优先
- 每行 `(宽+7)/8` 字节
- **每字节低位 bit0 对应最左侧像素（LSB-first）**

字库文件内部顺序必须严格等于 GB2312 一级字库顺序（啊…座，3755 字），
否则区位码索引会错位。生成后务必做一次逐字节回环比对。

### 如果 W25Q64 数据损坏

直接重跑第三节的烧录流程即可，无需修改任何代码——备份数据一直都在。

## 七、故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 屏幕只有纯色块，无任何文字 | 资源层未就绪 | 看串口 `[ASSET]` 日志 |
| `[ASSET] ERROR: W25Q64 not detected` | 芯片未焊接/接线问题 | 检查 PA4/PA5/PA6/PA7 与供电 |
| `[ASSET] ERROR: littlefs mount failed` | 未烧录资源 | 按第三节烧录；**固件不会自动格式化**（那会清空资源） |
| **全部 43 项都是 `MISSING ... err=-2`** | 资源从未烧录（`err=-2` 即 `LFS_ERR_NOENT`）。**littlefs 挂载成功不代表资源存在**——空的或旧的文件系统同样能挂载 | 按第三节完整执行三批烧录 |
| `[ASSET] MISSING /font/cn22.bin` | 该批次未烧录或中断 | 重跑对应批次 |
| `[ASSET] BADSIZE ...` | 文件不完整 | 重跑对应批次 |
| `[UI] WARN: asset layer not ready` | 同上 | 同上 |
| 全屏图出现撕裂/错位 | 双缓冲异常 | 检查 `ping-pong buffer ready` 是否打印 |
| 屏幕整体无反应 | LCD 未初始化 | 检查 `[UI] Board init done` 是否打印 |

**设计上刻意保留的安全行为**：
- 正式固件**绝不自动格式化** littlefs —— 挂载失败只报警，避免瞬时故障清空全部资源。
- 单个资源缺失只影响该资源（退化为背景色块），其余功能与网络、传感器照常工作。
- 不会因为资源问题死机或反复重启。

## 八、性能测量

`Profiling.c` 提供 DWT 周期计数器。测量方式：

```c
Prof_Init();                 /* Board_Init() 中已调用 */
uint32_t t0 = Prof_Cycles();
/* ...被测代码... */
printf("[PERF] %lu us\r\n", (unsigned long)Prof_Us(t0));
```

参考量级（SPI 21MHz，0.381 µs/字节）：

| 操作 | 字节数 | 纯传输耗时 |
|---|---|---|
| 22 号汉字字模 | 66 | 约 27 µs |
| 48 号 ASCII 字模 | 144 | 约 56 µs |
| 50×50 天气图标 | 5000 | 约 2.1 ms |
| 240×320 全屏图 | 153600 | 约 58.5 ms（双缓冲后总耗时也接近此值） |

实测时注意：字模读取还要叠加 littlefs 的 `seek` 开销（CTZ skip-list 遍历）。
若后续发现单字模耗时明显超过 200µs，可考虑加 4KB 块缓存（记录
`(文件ID, 块起始偏移)`，命中则零 Flash 访问）——ASCII 数字时钟的命中率会很高。

## 九、构建开关速查

`User/Inc/BuildConfig.h`：

| 宏 | 值 | 含义 |
|---|---|---|
| `USE_FREERTOS` | 1 | 正常运行 FreeRTOS |
| | 0 | 裸机模块测试（`BM_TEST_MODULE` 选择测试项） |
| `RESOURCE_DATA_IN_ROM` | 0 | 正式固件，资源不编译（**默认**） |
| | 1 | 编译资源数据（由 `RESOURCE_PROVISION` 自动联动） |
| `RESOURCE_PROVISION` | 0 | 正常运行 |
| | 1 | 进入资源烧录流程 |
| `PROVISION_BATCH` | 1/2/3 | 烧录批次，见第三节 |

**日常开发与发布都保持 `RESOURCE_PROVISION 0`**，只有在需要往 W25Q64 写资源时才临时打开。
